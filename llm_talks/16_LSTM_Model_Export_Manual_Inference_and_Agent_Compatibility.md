# LSTM Model Export, Manual Inference, and Agent Compatibility

**Source conversation:** `Download And Test Model`  
**Conversation date:** 29 October 2026  
**Scope:** Notebook assessment, LSTM checkpoint export, manual prediction workflow, and compatibility review of an existing agent package.

## Objective

The user wanted to assess an existing multivariate LSTM notebook, download the trained model, enter custom traffic metrics manually, and obtain a future request-count prediction. The user then asked to convert the training cell into a downloadable Python file without changing how the model works, and to determine whether an agent package built for another dataset could use the new checkpoint.

## Notebook assessment and reported evaluation

The notebook was rated **6/10**: it had a multivariate LSTM pipeline, a 60-row sequence, training/validation, baseline comparisons, and WAPE evaluation, but lacked a complete inference/export path and did not retain the ordinary LSTM model reliably.

The reported test WAPE values were:

| Forecasting method | WAPE |
|---|---:|
| Standard LSTM | **15.8%** |
| Moving average | 16.7% |
| Multi-feature GBM | 17.2% |
| Naive forecast | 18.4% |
| LSTM Q90 | 20.1% |

Lower WAPE is better. The standard LSTM led the listed methods, but its improvement over moving average was only 0.9 percentage points. The conversation explicitly cautioned that this test result did not establish performance on new traffic patterns.

## Model architecture and training behavior

The user supplied a PyTorch `MultiFeatureLSTMForecaster` training cell. Its core configuration was:

- Eight ordered input metrics: `requests`, `p50_ms`, `p95_ms`, `p99_ms`, `achieved_rps`, `app_cpu_pct`, `host_cpu_pct`, and `app_mem_mb`.
- `W = 60` historical observations.
- `H = 10` forecast steps.
- `DAY = 1440` for previous-day feature construction.
- LSTM hidden size `64`; one output head combining the final LSTM hidden state with four static/context features.
- Static features: standardized previous-day target, previous-day change, `sin`, and `cos`.
- `log1p` transformation of metric values; normalization using training-set `mu` and `sd`.
- Target based on a future log-traffic change, scaled by `dsd`.
- Adam optimizer with learning rate `2e-3`, 40 epochs, batch size 256, and a chronological 90/10 train/validation split inside `fit_lstm`.
- Two trained variants: standard LSTM with `nn.MSELoss()` and `lstm_q90` with pinball loss at quantile `0.9`.

The notebook's prediction target is **`requests`**. It does not directly predict CPU, memory, or replica count.

## Important timing and data-resolution issue

The notebook configuration treats rows as minute-level observations, but the sample `wallclock` timestamps shown in the conversation were about five seconds apart (`16:49:03`, `16:49:08`, `16:49:13`).

If those five-second records were used directly for training:

- `H = 10` represents about **50 seconds ahead**, not 10 minutes.
- `W = 60` represents about **5 minutes of history**, not 60 minutes.
- `DAY = 1440` represents about **2 hours of observations**, not one day.

The recommendation was to aggregate the raw data to one-minute observations and retrain before describing the model as a 10-minute forecaster. This timing issue was not silently corrected in the requested conversion because the user specifically asked to preserve model behavior.

## Checkpoint retention and export

The original training loop overwrote the variable `m` for each LSTM variant and did not populate the `lstm_models` registry expected by the final export cell. Consequently, after the loop, `m` referred to the last trained variant (`lstm_q90`), and the ordinary LSTM was not reliably retained.

The proposed minimal training-loop addition was to create `lstm_models = {}` and assign `lstm_models[name] = m` inside the loop. The rest of the training, prediction, and evaluation logic was to remain unchanged.

A checkpoint export cell was provided to save the standard LSTM to `lstm_requests_forecaster.pt`. The checkpoint metadata included:

- Model weights (`state_dict`) and model name.
- Feature order (`metric_cols`), target column, feature count, static-feature count, and hidden size.
- `W`, `H`, and `DAY`.
- Preprocessing values `mu`, `sd`, and `dsd`.
- Detected median sampling interval (`sampling_seconds`) when `wallclock` was available.

The export cell uses `google.colab.files.download()` to transfer the `.pt` file from the Colab runtime. The conversation also supplied links to `lstm_manual_test.py` and `colab_lstm_export_and_test_cells.txt`, but those helper files are not reproduced in this summary. The `.pt` checkpoint itself still had to be generated by running the export in the training runtime.

The user then asked for a converted `.py` training cell without behavior changes. A downloadable file named `lstm_training_cell_with_download.py` was provided. The stated changes were model retention and checkpoint export; the architecture, training, prediction, and evaluation logic were intended to remain unchanged. The user was told to run the earlier notebook cells defining `df`, `H`, `DAY`, `X`, `tr`, `te`, `preds`, `res`, and `score` before running the converted cell.

## Manual inference workflow

The proposed manual tester loads the checkpoint and a historical metrics CSV, then prompts the user to edit the newest row's eight metrics. The model uses that edited row together with the surrounding historical context to make a future `requests` prediction.

The prescribed CSV requirements were:

- At least **1,441 rows** for the current previous-day feature setup.
- All eight training metric columns in the same feature order.
- A compatible sampling cadence, checked against the checkpoint's saved `sampling_seconds`.

Example manual values in the conversation (`requests=180`, `p50_ms=35`, `p95_ms=90`, `p99_ms=130`, `achieved_rps=32`, `app_cpu_pct=78`, `host_cpu_pct=60`, `app_mem_mb=105`) were explicitly illustrative, not measured application data. Pressing Enter at a prompt was intended to preserve that metric's current CSV value. Entering one isolated row into a fresh model was not considered valid because the LSTM and previous-day features require historical context.

## Compatibility review of the existing agent ZIP

The existing agent was not directly compatible with the new `.pt` checkpoint. The old agent's prediction path imported `find_model`, `load_model`, and `predict_at` from `notebook/predict.py`, and expected its original dataset/model interface. The new LSTM instead required eight metrics per observation plus its saved preprocessing/context values.

The conversation identified these required integration changes:

1. Replace the old model-loading and prediction connector with a loader for the multi-feature LSTM checkpoint.
2. Supply all eight model input metrics in the trained feature order.
3. Reproduce the notebook's log transform, normalization, static features, and target reconstruction.
4. Convert forecast and observed request counts to a common per-minute rate before using the agent's replica-capacity calculations, because the existing scaling formulas assumed requests per minute while the new LSTM could be operating on requests per CSV row.
5. Align minute-based agent timers with the actual input sampling interval.
6. Keep the existing LangGraph workflow, unusual-traffic detection, decision limits, logging, alerts, and monitoring only where their interfaces remain compatible.

The conversation ended after identifying these mismatches and explaining that the agent needed adaptation. It did **not** establish that a fully adapted agent package had been completed or successfully run with this LSTM.

## Decisions, limitations, and pending work

**Decisions**
- Preserve the supplied LSTM's model behavior when converting its training cell.
- Retain both LSTM variants during training, but export the standard LSTM as the preferred checkpoint based on the reported WAPE.
- Bundle preprocessing metadata with model weights.
- Use a historical CSV plus editable latest-row values for manual inference.

**Limitations**
- The observed five-second sampling cadence conflicts with the notebook's minute-based `W`, `H`, and `DAY` interpretation.
- The existing agent's model/data interface and request-rate units do not match the new LSTM without an adapter.
- A strong notebook test WAPE does not demonstrate generalization to a different application's traffic.

**Pending**
- Run the training cell in Colab and generate the actual `.pt` checkpoint.
- Verify the manual inference helper against a compatible historical CSV.
- Retrain on correctly aggregated one-minute data if a genuine 10-minute forecast is required.
- Implement and test the agent adapter, including feature transformation and unit/timer alignment.
